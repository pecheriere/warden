# Security assessment

**Date: 2026-11-14. Covers release 0.13.0, reviewed at `main` commit `a401590`. The
release adds repository-scoped GitHub grants (risks 1 and 2, F24) and signs its manifest
through the broker (risk 12, below). The review for the previous release, 0.12.0, checked the ranked risks and findings against the changes
since 0.11.0: phone-approved releases (risks 1, 2 and 12). An agent can ask the owner to
approve one release, bound to a repository, a tag and a commit and checked against what
GitHub says; the broker then makes the tag, signs and attaches the manifest and publishes
the draft with release keys and a release App that it alone holds, one grant per release.
The accepted gap is that the agent's routine GitHub token can still publish a draft early,
which costs that version its manifest and not the integrity of a release (see
[Phone-approved releases](threat-model.md#phone-approved-releases)). The release is also
the first with the token renewal notice, a dependency update for RUSTSEC-2026-0486, and the
`warden setup` path fix, which move no risk. It ships OpenSSL 3.5.9, which five Low
advisories of 2026-11-10 affect, fixed in a 3.5.10 not yet released; they concern AES-GCM-SIV,
CMS and QUIC, which warden does not reach (it links OpenSSL only through webauthn-rs), and the
pin moves when 3.5.10 is out (#228). It did not repeat the full reading of the
documents against the code. Updated on the same day, for the next release, with `warden list`
and `warden prime` ([#246](https://github.com/pecheriere/warden/issues/246)): any agent key
can now list the targets and API secrets the owner has not hidden, with their addresses by
default, and ask whether warden covers a repository it names (risks 9 and 13, F25). See
[What an agent can learn about what warden covers](threat-model.md#what-an-agent-can-learn-about-what-warden-covers).
Updated on 2026-11-14 for the audit log's limits ([#265](https://github.com/pecheriere/warden/issues/265)):
proxied calls have a daily limit per API grant, and the entries of calls refused before they
start are limited. This adds risk 14 and F26 and moves the audit log rewrite to risk 15.**

**This is the project's own assessment. It is not an independent review, audit
or penetration test.** warden has not had one. The people and tools that wrote
warden also wrote this, so read it as a statement of what the project knows, not
as proof that nothing else is wrong.

**How it was done.** A coding agent, working for the maintainer, read the
documents against the source and looked at the project's alerts. Nothing was run
against a live deployment, the dependencies were read only where this page says
so, and no attack was attempted.

**When it is updated.** When a change moves a risk below (see
[`AGENTS.md`](../AGENTS.md)), and at the latest with each minor release. Change
the date at the top and say what the new version covers.

The [threat model](threat-model.md) says what warden protects and which risks are
accepted, and the [assurance case](assurance-case.md) gives the reasoning and the
code. To report a problem, see [`SECURITY.md`](../SECURITY.md).

## Ranked risks

Most important first, by how likely each one looks and how much damage it would
do. The ratings are judgement, not measurement. warden is young, with few users
and no incident history to learn from.

| # | Problem | Likelihood | Damage | What limits it | What you can do |
|---|---|---|---|---|---|
| 1 | **The owner approves something they should not**: a persuasive goal from a prompt-injected agent, or a reflex tap after many requests. | High | High: whatever the grant allows, for up to 4 hours. A commit signing grant lasts 30 days by default, up to 90, and a GitHub token grant 30 days at most. A GitHub token covers one repository of its grant, which the owner approves by name, and can still open issues (and, to be assumed, comment) on public repositories, installed or not (F22, F24). A release grant lasts one day and lets the broker sign and create one tag at one commit, sign a manifest of whatever the agent hashed, and publish a draft, all as the owner approved them on the phone | The scope is shown, read-only is the default, and the window is capped by the item. A session label and a link are shown as the agent's claim, and a link only to hosts the owner listed. The fingerprint is shown as words, easier to compare, with the same 48 bits. warden cannot judge a goal. | Read the scope. Keep items narrow, with short maximum windows and least-privileged accounts. Deny what you did not expect. |
| 2 | **A compromised agent machine uses a live grant**, for another task or for an attacker ([#49](https://github.com/pecheriere/warden/issues/49)). | High, if agents read untrusted content | Medium to high: bounded by the grant. A commit signing grant signs whatever the agent commits, with no prompt, for its whole window, and those commits show as verified. **A GitHub token is a credential the agent holds**: it works from anywhere for an hour, for one repository, and revoking the grant does not recall it, so a stolen one cannot be stopped but by suspending the App | Short windows, scope, audit. Secrets and credentials stay on the broker in proxy and relay modes. The commit signing key stays on the broker, signs only commits, and every signature is in the audit log. The GitHub App's key stays on the broker, tokens have fixed permissions (no workflows, no administration) and last an hour, and every mint is in the audit log, but a token cannot be recalled. The release key and the release App's key stay on the broker, which creates the tag and publishes itself and gives the agent no token; each release step runs once and is audited.  | One request per task. Revoke when done. Separate OS users and keys for work that must not share grants. Keep code review as the check on what lands: [a signature is not a review](threat-model.md#commit-signing). Install the GitHub App only on repositories you chose, with rulesets on GitHub that require your review: [the three levels](github-app.md#the-three-levels-per-repository). |
| 3 | **A deployment mistake removes a control**: an approval port an agent machine can reach, a listener another process can reach, or Funnel left on. | Medium: the setup has many steps, and warden cannot see the tailnet policy | High: the header can be forged. With it, an attacker can read the history and pending requests, deny and revoke, replace a request's approval link so that the owner's page fails, and show an agent's approval prompt to the owner on the wrong device. It still takes a passkey to approve. | `doctor` checks what it can, and [says what it cannot](configuration.md#checking-a-setup). The agent API and the approval listener refuse Funnel. | Follow [Deployment](deployment.md). Do the by-hand checks `doctor` lists. Test the tailnet policy. |
| 4 | **A certificate target accepts more than it should**: it trusts the CA for any principal. | Medium: a per-host setting that is easy to get wrong | High: an approval for one target works on others | Principals name the target. | [Set targets up](ssh-targets.md) for their own principal only, and test that another target's certificate is refused. |
| 5 | **Certificate access outlives its revocation, and its window** ([#35](https://github.com/pecheriere/warden/issues/35)). New logins work until the certificate expires. A login already open is not ended by revoking, by expiry, or by removing the CA. | Medium | Medium to high: new logins for at most 4 hours, but an open session, or a process it left running, has no time limit | Short windows limit new logins; the ephemeral key exists only in memory. Nothing in warden reaches an open session. Relay mode ends sessions. | Use relay mode where a session must be ended. In an emergency, [remove the CA and end the sessions on each target](assurance-case.md#the-ssh-ca-key). |
| 6 | **A vulnerability in a dependency that handles untrusted input**: `russh` on the relay (before login too), `axum` and `hyper`, `webauthn-rs` and OpenSSL. `rsa` is a pre-release through `russh`. | Medium | High, up to the broker: the broker can read the whole vault | Tailnet policy in front of every port. `cargo deny` nightly, Dependabot, memory-safe code. OpenSSL is pinned to a release of the 3.5 long-term support line, in place of 0.9.0's 3.6, whose support had ended. A check fails CI when that support ends, and fails the nightly run and the release 90 days before it or when a newer release of the line is out. The relay can be left off. | Keep up with releases. Narrow who reaches each port. Leave the relay off if you can. |
| 7 | **A bug in warden's own parsing or policy checks**: proxy rules, redaction, signature checks, the framing around P-256 verification, the CLI's `ssh-agent` client. Fuzzing is young and covers only part of this ([#91](https://github.com/pecheriere/warden/issues/91)), and coverage says which lines ran, not that their results were checked ([#97](https://github.com/pecheriere/warden/issues/97)). | Medium | Medium to high | Unit and integration tests, a scheduled fuzz job, Rust's memory safety, typed input. | Report what you find. |
| 8 | **The API origin handles the secret badly**, or a response leaks it in a form redaction does not catch. | Medium, depending on the API | Medium | Redaction, no compressed responses, exact origin. [The real control is the destination rule](threat-model.md#proxy-mode-residual-risks). | Give secrets the least scope the service offers. |
| 9 | **An agent's key is copied**: a bearer key, or a signing key kept in a file. It can use the agent's live API grants, within their scope and with the answers: writes too, if a live grant allows them. It can also list and revoke the agent's grants, list and cancel its requests, collect an approved API grant, sign commits under a live commit signing grant, mint GitHub tokens under a live GitHub token grant, list the targets and API secrets the owner has not hidden, with their addresses by default, and ask for more. It cannot approve anything, or use a live SSH grant without that grant's ephemeral key. | Low to medium: a bearer key is on the machine, or in its environment | Medium to high: bounded by what is live or later approved, up to 4 hours per grant, or the window of a commit signing or GitHub token grant, and the owner sees nothing new unless it asks for something | A bearer key works only with the owner's login. A signing key has no such check, only the tailnet policy. A key in hardware cannot be copied. Calls are audited under the agent's name. | Use a hardware key where the machine has one. Keep API grants short and read-only. `warden-server agent revoke` as soon as you suspect a copy. |
| 10 | **The warden host is compromised.** | Low to medium, depending on what else runs there | Critical: every secret in the vault, and the ability to issue grants. With the [local backend](local-backend.md), the secrets are on the host itself, with no read-only token boundary | Non-root, distroless, no capabilities, restricted egress, and private files. | Treat the host like your most sensitive target, and run nothing else untrusted on it. |
| 11 | **The vault or the Connect token leaks**, or Connect's traffic is read on a network that is not private. | Low | Critical: the same secrets | A token limited to one vault; isolated network. warden [refuses plain `http`](configuration.md#plain-http) to a host that is not clearly local or private, unless the owner opts in. | A read-only token for one vault. Connect on its own network, or over the tailnet or TLS. |
| 12 | **The release pipeline or a maintainer account is compromised.** warden has one maintainer. | Low | Critical for those who upgrade | Signed commits, protected branch, pinned actions, attestations, and from 0.9.0 a manifest the maintainer signs off GitHub. Nothing enforces that signing step. From 0.10.0 a release has more files (server, demo, `.deb` and `.rpm`). The server and the demo build only after the CLI, its packages and the image are attested, and the demo after the server, so the crates each one adds cannot change what was attested before them. That ordering covers nothing earlier: `ci` and the image build run all the workspace's build scripts before or alongside the CLI's build, and the packages are checked in the job that makes them ([not covered yet](verifying-releases.md#not-covered-yet)). The packages are not signed with a package key, so only these checks cover them. From 2026-11-08 a Homebrew tap installs the CLI. A published release's bump merges by itself once the tap's CI has checked its checksums against the signed manifest. The token that opens it can write to the tap only, and any change to the tap but such a bump needs the maintainer's signed commits. The commit signing key refuses tags and must not sign releases. 0.10.0 is the first release to run these jobs on a real tag. Releases made through the broker's release steps rest on a key that lives only in the broker and a phone approval, but **two things stay open**: the agent's routine GitHub token can publish a draft early and so cost a version (accepted, [threat model](threat-model.md#phone-approved-releases)), and until agents run as a separate user ([#186](https://github.com/pecheriere/warden/issues/186)) they can read the owner's `gh` token, which has administrator rights, and change a tag ruleset or make a tag without an approval. From 0.13.0 the manifest is signed through `warden release sign-manifest` with a key that lives only in the broker, listed in `docs/release-signers` under the identity `warden-release`; the earlier key of the maintainer stays trusted for earlier releases until it is retired from that file. | Pin the image by digest and [verify the release](verifying-releases.md), packages included. |
| 13 | **An enrolled agent floods the owner**: many requests and notifications, and disk use (risk 14). See F3 below. | Low: needs an enrolled key | Low: bounded at 60 notifications an hour per agent by default, which still makes risk 1 somewhat more likely | Dedupe per target or scope, and [per-agent limits](configuration.md#request-limits). Commit signing has a daily limit per grant and GitHub tokens an hourly limit of 60 per agent, and refusals beyond 30 a minute are counted, not recorded one by one, so none of them fills the audit log's disk or uses up the GitHub App's rate limit through mints. Asking whether warden covers a repository is not limited and mints a token at GitHub for each repository not asked about in the last 5 minutes, so it can use up that rate limit (F25). Listing pending requests or offers notifies nobody; each `GET /v1/offers` reads every target and API secret item, secret values included, and is not limited either ([#254](https://github.com/pecheriere/warden/issues/254)). Waiting long-polls are capped per agent, bodies read before their signature is checked share one budget, and each listener caps its connections, so that agents cannot stall the approval UI ([threat model](threat-model.md#authentication-of-callers)). Revoking the agent stops it. | `warden-server agent revoke`. Lower the limits if you see this. |
| 14 | **The audit log's disk fills or its lock stalls, and access stops for every agent.** The log is append-only and never rotated, and warden fails closed when it cannot be written, so anything that writes entries without a bound ends there. See F26 below and [the threat model](threat-model.md#what-the-audit-log-can-miss). | Low: proxied calls and relay sessions, the sources this risk covers, need an enrolled key and a phone-approved grant, and the entries they and refused relay logins write have a bound on size and on rate | High: no request, approval, proxied call or session can start until the disk has room or the log answers again. Revoking and the other ways of ending access go on | Proxied calls and relay sessions have a daily limit per grant (10000 and 1000 by default), each entry has a size bound (a proxied call's outcome is cut to 512 bytes, its URL and method too, and a relay session's command to 200 characters), and the entries of proxied calls refused before they start (30 a minute per agent), relay sessions refused after login (30 a minute per grant) and relay logins refused (5 a minute per address, 10 overall) are counted beyond that. Commit signing, GitHub token and release refusals and local backend errors are limited separately. The most each can write a day, from 2 MB for a relay grant to 67 MB for an agent's refused calls, is in [the threat model](threat-model.md#what-the-audit-log-can-miss). | Watch the disk and the audit log's growth, and alert before it fills. Revoking the agent stops its entries. |
| 15 | **The audit log is rewritten** by someone who controls the host. | Low | Medium: loss of evidence | The hash chain catches partial edits, but [not a whole rewrite or a removed last entry](threat-model.md#deployment-assumptions). | Ship the log somewhere the server cannot modify. |

## Findings of this review

What reading the documents against the code turned up. As far as reading the code
could show, none of these is a way in, but that is not proof: F6, for one, rested
on Tailscale behaviour that was not tested. Documents that were wrong are corrected
in the same change that added this page. The others need a code change or a
decision by the maintainer, and stay open until then.

| # | Finding | State |
|---|---|---|
| F1 | **The design overstated the approval binding.** It said the passkey signs a hash of the request and window. It signs a random challenge from `webauthn-rs`, and the binding is state on the server ([`approval/passkeys.rs`](../crates/broker/src/approval/passkeys.rs)). The threat model already said so. A broker that is trusted loses nothing, but the signature alone does not prove what was approved, so the audit trail cannot be checked that way either. | Document corrected. A signature over the request was [considered and not planned](design/passkey-binding.md). |
| F2 | **The design said a CA rotation procedure was documented. It was not.** | [Added](assurance-case.md#the-ssh-ca-key). Not yet run against a live deployment. |
| F3 | **Nothing limits how many requests an agent makes.** Dedupe is per target, and per secret and scope for API requests, so an agent can vary the path prefix, or cancel and ask again, and each new request notifies the owner. The `requests` table and audit log also grow without limit. No document mentioned it. | Fixed in [#113](https://github.com/pecheriere/warden/issues/113): [per-agent limits](configuration.md#request-limits), with what remains in the [threat model](threat-model.md#accepted-residual-risks). |
| F4 | **A certificate's `cert_issued` entry can be missing.** The approval is committed and audited first, then the issue entry is written; if that write fails, it is logged and the grant stands (`approve_finish` in [`approval/mod.rs`](../crates/broker/src/approval/mod.rs)). The design says each issue is audited. The `approved` entry names the grant, so the loss is small. | Fixed in [#114](https://github.com/pecheriere/warden/issues/114): the entry is written with the approval, and the certificate is not given out if it cannot be. |
| F5 | **Making an enrollment code is not audited**, though enrolling a passkey with one is. Only someone on the host can make one. | Fixed in [#114](https://github.com/pecheriere/warden/issues/114): `enrollment_code_created`, and no code without it. |
| F4a | **Ending access depended on the audit log.** Found while fixing F4. A revocation needed its entry written first, and writing the log could hold up other changes. | Changed on purpose: stopping access matters more than recording it. The entry waits in the database and reaches the log once it works, and the owner is warned until then. See [the threat model](threat-model.md#what-the-audit-log-can-miss). |
| F4b | **A proxied call or relay session did not check its grant again after recording its start.** A grant that ended during that write could still be used. | Fixed: both check again before anything goes out. |
| F6 | **The approval listener has no Funnel check.** Unlike the agent API, it relies on Funnel requests not carrying `Tailscale-User-Login`, as Tailscale documents. That was not tested here. Adding `refuse_funnel` to that router would make this independent of Tailscale's behaviour. | Fixed in [#115](https://github.com/pecheriere/warden/issues/115): the approval router refuses Funnel requests as the agent API does. |
| F7 | **`WARDEN_OP_CONNECT_URL` and the notifier URLs accept plain `http`.** This is deliberate for Connect on an isolated network, and for a local Home Assistant, but it was not written down as a choice. The approval link in a notification is useless without the owner's identity and a passkey. | Fixed in [#115](https://github.com/pecheriere/warden/issues/115): plain `http` is [refused](configuration.md#plain-http) unless the URL shows a local or private host or the owner opts in for that variable. |
| F8 | **The threat model said the broker holds the CA key in memory.** It reads the key at each approval and drops it after signing. Still true: anyone in control of the process can fetch it with the token. | Document corrected. |
| F9 | **The protocol said the owner may approve a *shorter* window.** The page offers any window up to the item's maximum, including one longer than asked. This is the owner's choice and is limited by the item, but an agent should not assume `not_after` is no later than it asked. | Document corrected. |
| F10 | **Open alerts at this date**, checked again on 2026-11-07. Five Scorecard alerts about project practices (CII badge, code review, maintained, vulnerabilities and branch protection), tracked under [#93](https://github.com/pecheriere/warden/issues/93). No CodeQL or Dependabot alert is open. | Open under #93. |
| F11 | **The reason on `deny.toml`'s `RUSTSEC-2026-0387` exemption is out of date.** It says "only Ed25519 is used", but P-256 signatures are verified through that code. Verification handles no secret, so the exemption still seems right. | Resolved by [#118](https://github.com/pecheriere/warden/pull/118), which removed `crypto-bigint` 0.5 and that exemption. |
| F12 | **`subtle` is listed in `[workspace.dependencies]`, and no crate uses it directly.** Still true at 0.13.0. | Harmless. For a code change. |
| F13 | **The documents said a copied bearer key can only create requests.** `proxy_call`, `list_grants` and `revoke_grant` in [`api.rs`](../crates/broker/src/api.rs) take the same `AuthedAgent` as creating a request, so any copied agent key can use the agent's live API grants and manage its grants. | Documents corrected, and the risk re-rated (risk 9). The code does what it should: a key is the agent. |
| F14 | **The documents treated a certificate's expiry as the end of access.** `sshd` checks a certificate when it authenticates, and not afterwards. On a throwaway OpenSSH 10.3 server on 2026-11-01, a session outlived its certificate's expiry, and outlived removing the CA with a reload, while new logins were refused in both cases. On OpenSSH 9.2 in a Debian 12 container, `usermod --expiredate 1` refused new logins and did not end an open session, and with `UsePAM yes`, `passwd -l` and `usermod -L` did not stop certificate logins at all. warden sees none of it. | Documents corrected, and risk 5 re-rated. [#35](https://github.com/pecheriere/warden/issues/35) covers what to do about it. |
| F15 | **Certificate logins are not in the audit log.** They go straight to the target, so warden records the issue and not the use. The target's `sshd` logs each login with the certificate's key id, `warden:<agent>:<grant id>`. Interactive input to a relay session is not recorded either. | Documents corrected. Ship the targets' logs if you need this trail. |
| F16 | **warden does not check the length of a pinned RSA host key.** An earlier draft of the [assurance case](assurance-case.md#key-lengths) said `ssh-key` refuses one under 2048 bits. That check exists only in a conversion this path does not use. It affects only keys the owner pins. | Documented. Refusing one at parse time would need a code change. |
| F17 | **The Pending page lets the owner's login do more without a passkey.** Found in review of [#145](https://github.com/pecheriere/warden/pull/145). With that login alone, someone can see pending requests, deny them, and keep replacing a request's approval link, so every page the owner opens fails before the passkey finishes. Where an agent has browser tools next to a usable passkey, the login can also raise a real prompt, and only the owner's attention stops it. | [Documented in the threat model](threat-model.md). It still takes a passkey to approve, and passkey prompts are limited per request. See risk 3. Not tested on a real phone. |
| F18 | **Commit signing had not reached this page or the design.** [#153](https://github.com/pecheriere/warden/pull/153) documented it in the threat model, but the ranked risks still said no grant lasts past 4 hours, and the design listed only the three access modes. | Corrected in the 0.10.0 review: risks 1, 2, 9, 12 and 13, and the design's opening. |
| F19 | **The CLI's `.deb` and `.rpm` had not reached the threat model.** [#165](https://github.com/pecheriere/warden/pull/165) documented them in the usage and verification guides only. | Corrected in the 0.10.0 review: [the threat model](threat-model.md) says what covers them. |
| F20 | **GitHub tokens break the rule that an agent never holds a credential**, which this page, the README and the assurance case relied on. The token is a bearer secret for an hour, covers every repository of the App's installation, and a revoked grant does not recall it. | Documented in [the threat model](threat-model.md#github-tokens) and [GitHub tokens for agents](github-app.md), and risks 1, 2 and 9 changed. The owner's setup on GitHub, not warden, bounds what a token can do. Checked against real GitHub on 2026-11-09: see F21 and F22. |
| F21 | **The deployment guide's egress rules left out `api.github.com`.** Found on 2026-11-09 by the first mint against real GitHub, from a broker whose egress was locked as the guide says: every mint failed with `503`. | Corrected: [the deployment guide](deployment.md#lock-wardens-egress) and [GitHub tokens for agents](github-app.md) say the broker needs it. |
| F22 | **A token can post on public repositories the App is not installed on.** Found on 2026-11-09: a token opened an issue on a public repository of the App owner's account outside the installation, since that takes only read access and an installation token can read public repositories. Other accounts' repositories were not tried. The documents said a token covers the installation's repositories. Since grants are scoped to repositories, see F24: it measured only a public repository the App is installed on, so F22 stays to be assumed for scoped tokens. | Documented in [the threat model](threat-model.md#github-tokens) and [GitHub tokens for agents](github-app.md#what-an-agent-gets). warden cannot narrow it. |
| F23 | **RUSTSEC-2026-0459, in the SQLite that `sqlx` bundles, has no reachable fix.** SQLite before 3.54.0 can return uninitialised memory when it opens a database with a crafted `-wal` file. `sqlx` 0.9.0 accepts only `libsqlite3-sys` below 0.38, and the fix is in 0.39. | Exempted in `deny.toml` with its reason ([#198](https://github.com/pecheriere/warden/pull/198)): warden opens only its own database, in a data directory it refuses to start in if others can write to it, and the CLI does not link SQLite. Remove it when `sqlx` takes the fix ([#197](https://github.com/pecheriere/warden/issues/197)). |
| F24 | **A GitHub token covered every repository of the App's installation.** Closed by repository-scoped grants ([#230](https://github.com/pecheriere/warden/issues/230), [#234](https://github.com/pecheriere/warden/issues/234)): a token is asked of GitHub for one repository id. Measured on real GitHub on 2026-11-11: a token for repository A got 403 creating a branch, opening a pull request, commenting or editing issues on B, and 404 reading a private B, but could still open a new issue on a public repository the App is installed on. That is the only public-repository case measured for scoped tokens; F22 still applies to be assumed (issues, and presumably comments, on public repositories the App is not installed on, anyone's). | Documented in [the threat model](threat-model.md#github-tokens) and [GitHub tokens for agents](github-app.md#what-an-agent-gets). What remains: the owner approving the wrong repository, issues, and presumably comments, on public repositories installed or not (F22, untested for scoped tokens), and a token valid for up to an hour per repository after a revocation. warden cannot narrow the first two further. |
| F25 | **Asking whether warden covers a repository spends the agent App's rate limit at GitHub, unlimited and unaudited.** Found in review of [#246](https://github.com/pecheriere/warden/issues/246). `GET /v1/offers/repository/{owner}/{name}` needs only an agent key. For each repository name not asked about in the last 5 minutes (the cache is shared by every agent, keyed on the name as given, so case variants count apart) the broker mints an installation token at GitHub and drops it. The call is not audited, and the 60 tokens an hour per agent do not count it, so an agent key cycling through names can use up the App's rate limit, which every agent shares, and delay or fail real mints. The shared cache also lets an agent tell from timing that some agent asked about a repository recently; the answer is the same for every agent. | Open, tracked in [#254](https://github.com/pecheriere/warden/issues/254). Documented in [the threat model](threat-model.md#what-an-agent-can-learn-about-what-warden-covers); nothing limits it yet. The server log records each call with the agent's name. |
| F26 | **A loop of proxied calls, or of calls refused before they start, could fill the audit log's disk.** Found in review of the audit log's limits. Each call that was sent wrote two entries, and each call refused by the policy, a changed secret or a limit wrote one, with no bound on how many in a day; the log is never rotated and a log that cannot be written stops every agent. | Fixed in [#265](https://github.com/pecheriere/warden/issues/265): a [daily limit of calls per API grant](configuration.md#optional) (`WARDEN_PROXY_MAX_CALLS_PER_DAY`, 10000 by default), and 30 entries a minute per agent for refused calls, the rest counted in `proxy_calls_refused_held`. A refusal quoting an agent's header name was first recorded whole, up to 64 KiB an entry; the outcome is now cut to 512 bytes, and the worst entry is about 1.5 KB. The sizes and the most proxied calls can grow the log in a day are in [the threat model](threat-model.md#what-the-audit-log-can-miss). |

## What this assessment did not do

- Test a live deployment (the OpenSSH behaviour above was tried on throwaway
  servers only), including the [systemd service](deployment-systemd.md),
  which is itself not yet tested on a clean host, or the procedures for
  [replacing credentials](assurance-case.md#7-replacing-credentials).
- Review the dependencies, beyond the algorithm lists quoted in the
  [assurance case](assurance-case.md#6-cryptography).
- Review Tailscale, 1Password Connect, or how browsers and authenticators
  implement passkeys. warden relies on all of them.
- Check what dependencies log above the default level.
- Check every line of the relay's flow control and teardown against the design.
  The claims there were spot-checked, and rest on the relay's tests.
- For 0.10.0, and still not done at 0.13.0: sign a commit through a live broker and
  check it on a real GitHub account, install the `.deb` and `.rpm` on a clean host, or test the release binary's
  name resolution on a tailnet. The commit signing, label, link, pending list and
  fingerprint changes were checked against their threat model sections and tests, not
  against a deployment.
- For GitHub tokens: check what a ruleset does to a token, or run `warden setup github`
  and the `gh` wrapper on a real agent machine. On 2026-11-09 a token minted from a real
  App, with its key in a concealed 1Password field read through Connect, matched the
  permissions asked for in every operation tried (a branch, a commit, a pull request and an issue worked; a workflow
  file and a repository setting were refused), and `git push` through `warden
  git-credential` worked. The cache and the wrapper were checked against a fake GitHub and
  the code's tests, and the [threat model](threat-model.md#github-tokens) section against
  the code.
